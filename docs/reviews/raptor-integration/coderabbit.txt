  Process termination on allocation failure is unacceptable in library code.

  All incremental context init and clone functions (shake128_inc_init,
  shake128_inc_ctx_clone, shake256_inc_init, shake256_inc_ctx_clone, and
  their SHA3 counterparts) call exit(111) when malloc returns NULL. This
  terminates the entire process instead of allowing the caller to handle the
  error gracefully.

  In a production system, memory allocation failures should propagate error
  codes (e.g., return -1 or NULL) so that:
  - The application can log the error and retry
  - Other parts of the system can continue operating
  - The process can shut down cleanly

  This pattern is repeated throughout the file (lines 527-528, 547-548,
  559-560, 579-580, 602-603, 626-627, 650-651, 674-675, 749-750, 757-758,
  810-811, 818-819, 871-872, 879-880).

  While this is a known PQClean implementation choice for simplicity, it
  creates a critical stability risk when integrated into a long-running
  service or embedded system where malloc failure should not be fatal.





  💡 Recommended mitigation strategy

  Consider one of the following approaches:

  Option 1 (preferred): Modify the vendored code to return error codes:
  - Change all _init and _clone functions to return int (0 on success,
  -1 on error)
  - Replace exit(111) with return -1
  - Update all callers in the shim layer (raptor_falcon.c) to check return
  values

  Option 2: Pre-allocate contexts on the stack or in caller-provided
  buffers:
  - Change context types from pointers to fixed-size arrays
  - Remove dynamic allocation entirely
  - This matches the approach used in some other PQClean variants

  Option 3: Document the risk and ensure the build environment guarantees
  allocation success:
  - Use memory overcommit on Linux
  - Pre-allocate a memory pool for crypto operations
  - Monitor available memory and prevent operations when low
  - Accept that OOM will terminate the process
